# Private Cloud Backup and Restore

1. Activate only for the user's cloud backup, restore, connection or inspection request. Do not run or recommend it during ordinary coding, phase completion, local backup completion or merely because a connection exists. Do not add timers, hooks, watchers or background retries. Existing doc-driven roles remain unchanged.
2. Read docatlas private-cloud help (or npx docatlas private-cloud help). If the installed version has no helper, report the version gap; do not invent archive/extraction scripts. Helpers return JSON: 0 complete/unconfigured, 1 failure, 2 usage, 3 needs attention. Stop on 3 and resolve the reported choice or blocker.
3. List connections, then inspect status for the selected name. Reuse the requested name or the only saved connection; ask when several are plausible. If missing, ask for a cloud service/folder or backup file location. Code and OS do not reveal an old account. Help the user connect their existing cloud app; do not scan their entire home or log in for them. Check the actual local folder and system tar.
4. Use projects --directory to discover project keys and named collections, then list with --directory, --key and --name as needed. Recovery lists identify tags, devices, history and archive locations. Match the repository key; origin-less or renamed repositories may need the old key. Do not infer latest from clocks or choose between divergent heads.
5. Connect only the selected target. Configuration authorizes no subsequent automatic work. Names default to default; different names isolate backups for the same repository. Use --tag for a backup label or --bundle for an immutable version ID, not a Git checkout. Keep existing tags; ask for an ID if a tag is ambiguous.
6. On a cloud backup request, run backup with the chosen --name and optional --tag. If the helper reports unhidden private files, run the existing private init and check its result first. Keep private files out of git and keep machine paths/credentials out of tracked configuration. Report unchanged or the prepared archive and ID.
7. Archives are plain, unencrypted tar files with equal content stored once. The helper validates imports and reconstructs local hard-link sharing. A cloud-folder file means prepared, not uploaded. Ask the user to check the cloud app's delivery state when needed before changing PCs. Never delete remote archives.
8. On restore, select the matching name and tag/ID, run restore without --apply, and show the read-only preview. Apply after the user agrees. Preserve conflicts unless the user explicitly requests replacement; only then add --force, which saves a before-restore backup. Unlisted local files remain. Bad checksums, unsafe paths and incomplete downloads are blockers.
9. Record/report success only from the helper result. It saves the new machine's connection after a successful apply. A home/work workflow uses an explicit backup request, delivery confirmation, and an explicit restore request. Do not automatically merge, force restore, check out code, or upload local changes to resolve a conflict.
10. Respect operation locks. Inspect status instead of deleting a lock by age. Only use unlock with the displayed ID when the user asks to recover interrupted work and the helper confirms the owner stopped. Do not treat old state records as evidence that current files are valid.
11. backup/restore accept repeated --path values relative to .docatlas/private. Omit the option for all source paths. Apply only selected files at their original locations and keep other local folders. Public docs/ is outside this skill. Restoring a into a folder containing c leaves a,c; do not delete b or c if they already exist.
